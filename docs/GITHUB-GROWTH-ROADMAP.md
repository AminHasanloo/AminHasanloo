# GitHub Growth Roadmap

The goal is a profile that proves useful engineering work. Achievements are a side effect, not the product.

## Already visible

- Developer Program Member
- Pull Shark x3
- YOLO

## First 7 days

- Pin six repositories that match the Unity, game AI and automation direction.
- Enable private contribution counts if that visibility is wanted.
- Enable Discussions on the profile repository or the strongest public tool repository.
- Run the profile visuals workflow once and confirm both generated SVGs render.
- Replace outdated repository descriptions and add accurate topics.

## First 30 days

### Public project quality

- Add a 20–40 second demo GIF or clip to the Vehicle AI repository.
- Add a clear Quick Start and compatibility table to each main Unity repository.
- Publish one real release with version notes and a tested Unity version.
- Add one small architecture diagram and one troubleshooting section per main project.

### Community participation

- Answer focused Unity, C#, game AI, Spine or automation questions where there is real experience to share.
- Prefer a short working example, profiler evidence or a repository reference over generic advice.
- Start Discussions around genuine design choices such as vehicle recovery, data-driven simulation or SDK isolation.
- Mark answers only because they solved the question, never as an achievement shortcut.

### Sustainable cadence

- One meaningful public improvement each week.
- One evidence-backed devlog when there is something worth showing.
- One release or demo improvement each month.
- Review repository topics, screenshots and setup instructions monthly.

## Achievement paths that fit the work

| Achievement | Authentic path |
|---|---|
| Pull Shark | Merge focused PRs for real features, tests and docs. |
| Pair Extraordinaire | Use co-authored commits only when a real collaborator contributed. |
| Galaxy Brain | Give useful Discussion answers that another maintainer accepts. |
| Quickdraw | Resolve a real issue quickly when the fix is genuinely clear. |
| Starstruck | Improve demos, onboarding and releases so useful repositories earn real stars. |

## What automation should and should not do

Automation can refresh profile graphics, maintain one weekly shipping queue, check links and surface relevant discussions. It should not create fake PRs, self-answer questions from another account, manufacture co-authors or post generic replies. Those patterns reduce trust even if a badge appears.

## GitHub-native automation now active

- `profile-visuals.yml` refreshes the contribution snake and public telemetry every day.
- `profile-health.yml` checks local assets and public profile links every week, maintains one health issue and closes it after recovery.
- `weekly-focus.yml` maintains one rolling shipping queue instead of generating issue spam.
- `dependabot.yml` asks GitHub to open focused update PRs for pinned GitHub Actions references.

These jobs improve maintenance and visible project health. Their bot activity is intentionally not presented as personal engineering contribution.
